# ADR-002 — стратегия кеширования

- **Дата:** 2026-10-19
- **Статус:** **Предложено**, требует согласования CTO/Product/Безопасность; не подтверждён эксплуатационными испытаниями.
- **Связь:** [ADR-001 — модульный монолит](../Task2/adr-001-architecture-style.md), [SLO каталога](slo/catalog.md), [FMEA](fmea.md); ограничения Task1 R-22 (3G/изображения), R-09 (SLO), R-10 (размещение данных).

## Контекст
Дешёвые Android/3G, быстрый каталог и рекламные всплески повышают ценность кеширования. Но кеш некорректных цен или складских остатков на оформлении заказа может привести к потере денег. Универсальная Redis-инфраструктура увеличивает регулярные затраты и операционные риски при лимите CFO 5 000 долларов США в месяц.

## Решение
CDN и пограничный узел кешируют **только публичные** статические активы и анонимные ответы; серверное приложение реализует кеширование по запросу (Cache-Aside) для с большим числом чтений каталога с ограниченный кеш LRU в памяти процесса как первичным вариантом, без обязательного Redis. Изменения каталога инвалидируют теги/ключи после фиксации транзакции через журнал исходящих событий; при потере сбоя инвалидации TTL остаётся верхней границей устаревания. Платежи/заказы/персональные данные/пользовательские данные **не кешировать** на общих промежуточных узлах.

| Объект | Место | TTL / директива | Инвалидация и защита |
|---|---|---|---|
| Изображения SKU (версионный URL) | CDN + браузер | 7 суток, неизменяемый при хэше | новый asset URL по изменению, очистка кеша при юридически обязательном удалении |
| JS/CSS с content hash | CDN + браузер | 30 суток неизменяемый | новый build hash |
| Публичная карточка/категория | Edge/private service LRU | 60 с, случайный разброс ±20%; показ устаревшего содержимого с фоновым обновлением максимум 60 с **только для просмотра каталога** | после фиксации транзакции event `ProductChanged` очистка кеша SKU/tag; TTL fallback |
| Категорийная навигация/справочники | Серверный LRU | 10 мин | version increment + manual сбоя инвалидации |
| Поиск/листинг (анонимные и легальные) | Пограничный/серверный | 30 с | tag/publish event, capped cache keys |
| Наличие/цена на странице | Серверный кеш чтения | **≤5 с** (предварительный максимум) | после изменения stock/price удаление ключа; оформлении заказа **всегда повторно читает транзакционный первичный источник данных** |
| Персональные корзины/оформлении заказа/auth token | **не общий кеш** | `Cache-Control: запрет хранения` | durable DB, encrypted session if needed; no cached payment success |
| KYB/consent/PII/settlement/ledger | **не общий кеш** | запрет хранения | база данных и аудит, no public CDN |
| Статус платежа у PSP | **не кешировать как факт оплаты** | запрет хранения | проверенный подписанный вебхук и сверка |

**Ключ кеша:** `country:locale:catalog-version:sku/filter-hash`, теги стране/языку; не смешивать персональные данные Нигерии и Кении. CDN cookie удаляются из ключа публичного кеша только для публичных GET-запросов; Vary correctly; предотвращать отравление кеша by normalized query/key length. Use кеширование отсутствия объекта 404 ≤10s for public SKUs only. Объединение одновременных запросов к одному ключу, bounded size and квоты по странам protect origin against stampede.

## Отвергнутые альтернативы
1. Без кеша: проще в операциях, но риск p99/3G и избыточной нагрузки на DB.
2. Redis для всего: не нужен без измеренных hit ratio/latency, дороже и создаёт отдельный failure domain; Redis может быть выбран позже только после экспериментального сравнения.
3. Длительное кеширование остатков/платежей: неприемлем для корректного платёжного пути.

## Последствия
**Плюсы:** дешевле, меньше обязательных сервисов, отзывчивее чтения, простой rollback и CDN bandwidth control. **Минусы:** ограниченная когерентность после изменения каталога; версионность и журнал исходящих событий events обязательны; in-process LRU живёт отдельно на каждом instance; очистка кеша CDN может быть eventually consistent.

## Критерии проверки и пересмотра
Нагрузочный тест 100 RPS baseline и 2× burst, p99 каталога ≤1s, cache hit ratio ≥70% на **репрезентативном browse** (только цель испытаний), отсутствие stale price/stock в 100k оформлении заказа replay cases. Пересмотреть Redis/выделенный caching tier при устойчивом miss pressure, экономически обоснованной цене, одобренном CFO run-cost и подтверждённом legal region. При изменении policy страны запрещать CDN edge caching регионально до legal approval.
